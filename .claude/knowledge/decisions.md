# Decision log

Append-only. Format: **Dn: decision.** Why. Alternatives considered. Date.
If you reverse a decision, add a new entry that references the old one. Don't edit the old one.

**D1: Phone app = Expo (SDK 58, RN 0.88, React 19.3) with a development build (`expo-dev-client`), not Expo Go.**
The team knows React/TS, fast refresh works over USB/Wi-Fi, and Expo modules cover most needs. Expo Go can't load the native
modules we need (notify-kit, custom plugins). Alternatives: a PWA (can't wake the phone, background sockets die, no notifications
without HTTPS), Flutter (new language for the team), native Kotlin (best for deep Android features but slower to build UI), and
Capacitor (weaker background story). 2026-11-06.

**D2: Continuous Native Generation.** `frontend/mobile/android/` is generated by `expo prebuild` and gitignored. All native config
goes in `app.json` and config plugins (`frontend/mobile/plugins/`). This keeps builds reproducible on any teammate's machine with no
merge conflicts in native files. 2026-11-06.

**D3: Notifications, foreground service and full-screen intent = `react-native-notify-kit`.** `@notifee/react-native` was archived
by Invertase on 2026-04-07 (last release Dec 2024, old architecture). `expo-notifications` 58 has no full-screen intent and no
foreground service. notify-kit is the maintained, Notifee-API-compatible, New-Architecture fork with an Expo config plugin, validated
on RN 0.88. 2026-11-06.

**D4: `expo-notifications` is installed only to create alarm-usage channels + bundle sounds.** notify-kit creates channels with
`USAGE_NOTIFICATION`, which silent/vibrate mode mutes. expo-notifications supports `audioAttributes.usage = ALARM` and copies custom
sounds into `res/raw`. Notifications are still posted with notify-kit on those channel ids. 2026-11-06.

**D5: In-app audio = `expo-audio`** (expo-av is removed). Sounds are generated deterministically by `tools/gen-sounds.mjs`
(2.8–3.6 kHz beeps, the band where hearing is most sensitive) and shared with the dashboard. 2026-11-06.

**D6: Local Gradle builds, not EAS cloud.** No account and no queue, and iteration is faster. The toolchain is the Android SDK
cmdline-tools + a portable JDK 17 registered as a Gradle toolchain. See `environment.md`. 2026-11-06.

**D7: Transport = plain WebSocket + JSON** (FastAPI native). No Socket.IO/SignalR. The starter's `useSignalR` hook gets replaced by a
`useCarSocket` hook with the same never-give-up retry semantics. 2026-11-06.

**D8: One adapter per client (`src/protocol/normalize.ts`).** The backend contract is unknown, so only that file knows the wire
format. The UI tolerates any subset of metrics and unknown keys, with a client-side fallback level when `risk` is missing. 2026-11-06.

**D9: Dashboard = the user's Vite starter** (Vite 8, React 19, Tailwind v4, shadcn, Hugeicons), copied from `fh26/extracted`.
Sounds use the shared WAVs or Web Audio. Browser autoplay rules need one user click to "arm" sound. 2026-11-06.

**D10: Defaults.** Dark UI, English strings, orientation `default` (car mounts are often landscape), package `dev.hakaton.driveralert`,
display name "Driver Alert" (a placeholder; rename freely, but changing the package means a reinstall). Default server
`localhost:8000` (USB + `adb reverse`). 2026-11-06.

**D11: Android only.** No Mac. Also, iOS can't wake the screen or run a foreground service without Apple's Critical Alerts
entitlement. The WebSocket protocol is platform-neutral, so iOS could join later as a basic client. 2026-11-06.

**D12: Build only `arm64-v8a`** (`expo-build-properties.buildArchs`). That's 4× less C++ to compile, and every current phone is arm64.
Add `x86_64` if someone needs an emulator. 2026-11-06.

**D13: Foreground-service types `location` + `specialUse`.** `location` is Doze-exempt with no timeout and is legitimately used for
GPS speed. `specialUse` is the fallback if location is denied (fine for sideloading). Don't use `dataSync`: it has a 6 h budget and no
Doze exemption. 2026-11-06.

**D14: Flashing stays ≤ 3 Hz (2 Hz in practice).** Photosensitive-seizure safety (WCAG 2.3.1), and the user is driving. Sound is the
primary channel and the flash is secondary. 2026-11-06.

**D15: `docs/API.md` (backend-owned) is the contract. This supersedes the frontend draft `ws-protocol.md` and parts of D7/D8.**
The real backend landed on 2026-11-06 (commit `903df76`): a 0–100 attention score, six levels, behaviour labels instead of probabilities,
WS `{type, data}` with `trip_started|state|emergency|trip_ended`, and client messages ignored. So: no client-side fallback scoring (the
app shows `response`), no hello/ping/sim messages, and no mock server (the backend + `notebooks/safety_client.py` simulator replace it).
Still valid from D7/D8: plain WebSocket, never-give-up reconnect, and only `src/api/` knows the wire format. 2026-11-06.

**D16: Backend on this laptop runs in `backend/.venv` with Python 3.13** (installed with `py install 3.13`). Python 3.15 failed because
PyYAML (pulled in by `fastapi[standard]`) has no cp315 wheel. The backend docs also target 3.13. 2026-11-06.

**D17: The app display name follows the team's project name, "Safety Reviewer".** This supersedes the "Driver Alert" placeholder in D10.
The package id stays `dev.hakaton.driveralert` and the scheme stays `driveralert`, which avoids a reinstall and is invisible to users. 2026-11-06.

**D18: Swap the SDK CMake's Ninja for 1.13.2 instead of moving the repo to a short path.** The first build failed on the Windows
260-char limit (`ninja: error: mkdir(CMakeFiles/rnscreens.dir/C_/Users/...)`). Long paths were already enabled in the registry, but
Ninja 1.10.2 isn't long-path-aware. Swapping the binary in every SDK CMake (3.22.1 + 3.30.5) needs no admin rights and keeps the user's folder layout.
Alternatives: move or `subst` the repo (disruptive; subst risks mixed real/virtual paths in CMake). 2026-11-06.

**D19: Trip report storage is Postgres + S3-compatible object storage (RustFS), not a vector database.** The report asks "where was it
worst, what was the worst thing, show charts and clips". Those are plain SQL queries over per-second samples and per-moment rows, plus
files in a bucket. A vector DB only pays off for similarity search over embeddings. If that's ever needed, use pgvector in the same Postgres.
MinIO was rejected because its Community Edition went source-only in Oct 2025 and its repo was archived in Feb 2026. RustFS 1.0.4 is
Apache-2.0, S3-compatible and has a Windows build. 2026-11-06.

**D20: One sample row per second, not per 0.5 s.** Ticks arrive ~2/s, so 0.5 s windows would store raw ticks. Each 1 s row keeps both the
average and the maximum (p, risk, light, sound), so a short glance isn't averaged away. Exact moments live in `risk_events`. 2026-11-06.

**D21: The backend owns the speed.** The camera can't know it, and asking the CV team to fake it makes no sense. The default is a mocked drive:
six keyframe scenarios with cubic Bezier easing, picked per trip and including real 0 km/h stops. The phone's GPS (`POST /speed`) is an
opt-in feature (`PHONE_SPEED_ENABLED`), meant for cars without their own compute. Precedence: fresh phone reading > tick's `speed_kmh`
(simulator) > mock. 2026-11-06.

**D22: Clips reach the app through the backend (`/api/v1/media/...`), and the services run portable on the demo laptop.** Port 8000 is
already allowed through the Windows firewall and follows the hotspot IP. A direct S3 URL on :9000 would need a firewall rule and a
host that changes per session. The bucket is still public-read for the demo, as asked. Docker isn't installed on the demo laptop, so
`backend/scripts/services.ps1` runs Postgres 18.6 + RustFS from `%LOCALAPPDATA%` without admin rights (outside OneDrive, so the database
files never sync). `docker-compose.yml` mirrors it for teammates. Postgres uses 5433 because a system Postgres holds 5432. 2026-11-06.

**D23: Accounts use opaque DB-backed tokens and scrypt, and login stays optional.** Each token is 32 random bytes; Postgres stores only its
SHA-256, with a 30-day expiry. Compared with JWT this needs no signing secret, and logout really ends the session. Passwords use
`hashlib.scrypt` from the stdlib (no new dependency), run in a worker thread so they never stall live scoring. A trip started with a token
is private to that account: others get 404, so its existence isn't leaked. Trips without a token stay public, so the simulator,
`tools/sim.py`, the dashboard and the not-yet-updated app keep working. The live path (WS, telemetry, ending a trip) stays open because
it's the car's own network. 2026-11-06.

**D24: The report sends raw per-second samples, and the app draws the charts.** `GET /trips/{id}/report` returns the whole session
(summary, user, samples, moments with images) in one call, so the backend never has to know what charts the app wants. "Raw" means the
1 s rows of D20. If every tick (~2/s) is ever needed, set `sample_window_s = 0.5`. The `trips` row also gets a running summary every ~10 s,
so a crash mid-trip still leaves a usable summary, and the next start closes such trips. 2026-11-06.

**D25: The trip-level model report lives in the backend; the CV pipeline only does per-frame math.** The pipeline used to build
`summary.json` / `events.jsonl` itself (`RiskEngine.summary`, `_category_event`, alert episodes). That code moved to
`backend/app/services/model_report.py` and runs on the frame stream of `POST /telemetry` (stored in `trips.model_report`, returned as
`TripReport.model`), so live trips, history and offline runs use one implementation. Alternatives: keep it in the pipeline and upload a
summary at the end (lost if the pipeline crashes, and it doesn't know the speed), or recompute from `trip_samples` (1 s rows lose the
model's on/off transitions). The module is stdlib-only, so the pipeline's dev mode imports it to print the same report locally. Checked
against the old pipeline on 62 recorded runs: identical episodes and alert episodes; summary numbers equal up to rounding. Standing
time (< 5 km/h) is excluded, like every other statistic. `peak_p` is the raw `p` (the app's `camera` view has no `p_hat`). 2026-11-06.

**D26: `risk_pipeline.py --mode dev|prod`.** dev = window with a reduced overlay (`notebooks/dev_overlay.py`: alert + risk, rules,
5 categories, 4 signals, 30 s risk line; ROIs behind the R key) and a full `frames.jsonl`. prod = headless, no overlay import, sends a
slim frame record (only the `ModelFrame` fields) ~2/s plus every alert change, and JPEG video ~8/s, from two background threads with
small drop-oldest queues, so a slow backend never stalls the camera. File sources run at recording speed in prod (sleep when ahead,
skip frames when behind), so tick time and clip time stay aligned with the backend's clock. 2026-11-06.

**D27: The backend is split into a coordinator (in the car) and a server (storage/report); the model is its own process.**
Requested by the user (2026-11-06 evening). The coordinator owns everything live: the phone WS, the camera stream, the model link,
risk + score + car response, a 5 min video cache, and 2 s section summaries. The server owns Postgres + S3, accounts, history and
the report. They talk only over HTTP (`/internal/trips/{id}/sync`, `GET /auth/me`); in one process via `httpx.ASGITransport`, split
via `SERVER_URL`, so separating them is configuration, not code. The demo keeps one process on :8000 so the phone keeps one address.
Alternatives: two processes now (two ports through the firewall and hotspot, and the app would need two addresses) or a direct
in-process call (no real boundary). Supersedes the in-process `TripRecorder` that wrote to Postgres from the live process; D25's
model report moved with it into the coordinator (the module itself stays at `app/services/model_report.py`, which the CV dev mode
imports). Both camera paths stay: `risk_pipeline.py --mode prod` → `/telemetry`, or camera → coordinator → model worker. 2026-11-06.

**D28: The model worker dials into the coordinator over a WebSocket (`/api/v1/model/ws`), one frame in flight, newest frame wins.**
Dialing in needs no new port or firewall rule (port 8000 is already open, which matters for a GPU laptop or a container), and
either side can restart. Binary frames (uint32 header length + JSON header + JPEG), JSON detections back. A slow model never builds
a queue, so detections are at most one frame old. Alternatives: the model as a server the coordinator calls (new port), gRPC,
ZeroMQ or Redis queues (extra dependencies). 2026-11-06.

**D29: Sections of 2 s replace the 1 s samples and the clip-based risk events; moments are derived on read.** The user asked for a
summary every 2–3 s, an image for dangerous parts, and a chart with nodes and pictures for the ultra-dangerous parts. 2 s keeps
10–20 model detections per section, gives 900 points per half hour, and gets a dangerous moment to the phone and server within
~2 s. Danger is decided by the coordinator (critical = model red alert, loud alarm or emergency; dangerous = scored behavior, yellow
alert or vibration; only while moving). Back-to-back dangerous sections (bridging one quiet section) become a moment when the server
reads the report, so there is no second table to keep consistent. Clips are dropped for now (the user scoped "video of the whole
section" as a future fix; `VideoCache.frames_between` + `encode_mp4` are kept for it). 2026-11-06.

**D30: The video cache is diskcache on disk (5 min, 1 GB, 10 fps max), not Redis.** At 10 fps of ~50–300 KB JPEGs, 5 min is
150–900 MB: too much for memory, while diskcache keeps a bounded, FIFO-evicted cache in a temp folder with no extra service. Writes
go through one worker thread so the event loop never waits for the disk; the frame the model analysed is always kept (it may become
the section image). Section aggregation stays in memory (tiny, per trip). Redis Streams would be the next step if several
coordinators ever need a shared cache. 2026-11-06.

**D31: The CV team's `RiskEngine` is copied into the coordinator, not imported, and a test keeps the copy identical.** The user
asked to extract the final-score logic without editing the CV code. The coordinator must not depend on numpy/OpenCV or on
`notebooks/` at runtime, so `coordinator/services/risk_engine.py` is a verbatim copy of the per-frame engine (after D26 it has
no trip statistics and no numpy). `tests/test_risk_engine.py` replays 5 × 4000 random evidence steps through both and requires
equal records. The whole-trip statistics are D25's `app/services/model_report.py`, which the coordinator now feeds with every tick
(model worker detections and `/telemetry` frames alike) and ships to the server with each section. The worker imports the CV
detectors (`FeatureExtractor` etc.) straight from `risk_pipeline.py`. 2026-11-06.

**D32: The drive chart on the phone uses `react-native-svg` (native rebuild), not plain Views.** A line + gradient area + shaded
sections + nodes + dashed connectors is natural in SVG and impractical with Views. Expo SDK 58 pins `react-native-svg` 15.16.0;
the incremental dev build took 1 min 50 s. The image boxes are RN `expo-image` views over the SVG (caching, tap targets). The web
dashboard draws the same chart with plain inline SVG. 2026-11-06.

**D33: On this laptop Postgres + RustFS run in Docker (`backend/docker-compose.yml`).** Docker Desktop is installed now (D22
assumed it wasn't); the portable `services.ps1` stays for the backend teammate's laptop. Same ports and keys either way. 2026-11-06.

**D34: The demo and the architecture use one camera path: camera → coordinator → model worker → coordinator.** The user defined
it: in the car are the camera, the model and the coordinator; the server is outside and holds history and logs. Video goes only
into the coordinator, which sends frames to the model, gets evidence back, computes risk + score, streams it to the phone, decides
which 2 s sections are dangerous and posts their picture to the server, which stores and serves it. The coordinator owns all
caching (video window, outbox); Postgres + RustFS are the server's only. The CV teammate's `risk_pipeline.py --mode prod` (the
pipeline scores itself and posts frame records to `/telemetry`) is **debug only**; the coordinator refuses those records with 409
while a model worker is connected. Alternative (keep both as equal demo paths) dropped: two places computing risk, and they
silently double-scored a trip when both ran. Follow-ups in the same pass: a phone login never blocks the car (stale-if-error token
cache; an unchecked token travels as `TripMeta.owner_token` and the server resolves it), video frames also expire on housekeeping.
Still open: outbox on disk and the phone's second address once the server really runs elsewhere. 2026-11-06.

**D35: The score is a live reading of the current situation, not a points balance.** User's request: "score is not gamification, it goes
up and down depending on the current situation; speed is a scaling factor; at 0 km/h nothing warns". The old model (weight × seconds,
onset hit, fragility, +3/min recovery after 30 s) only ever fell during a drive. Now: danger = worst behaviour (growing with its
duration) + 30 % of the rest, or the CV risk engine's risk (minus its calm 0.1, ×0.8); × speed factor (0 below 5 km/h, 1 at 50, 1.6 at
130) × night 1.25; score follows 100 × (1 − exposure) with τ 0.5 s down / 2.5 s up. Calibrated on the fake worker at fixed speeds and
on the A54 (critical with the phone in town, back to safe ~6 s later). Reaction thresholds (≥ 5 s / ≥ 2 s) dropped: the level already
encodes duration; vibration/sound only while something risky happens. Summaries headline `average_score` (moving time) and `level` is
for it, because the live score at the end is ~100. Alternatives: keep the balance with faster recovery (still "never goes up" while
driving), or show the model's risk directly (no speed, no labels from the simulator). 2026-11-07.

**D36: The phone app requires an account.** Register/login screen first, token on every REST call (401 → back to login), logout in
Profile, history = my trips. Trips from the app always belong to the account; the backend keeps accepting token-less trips for the
simulator and the dashboard sim panel. Token in AsyncStorage, not expo-secure-store (would be a new native module = rebuild; fine for
the demo). `run.py --mock` starts the mocked camera + fake model with the backend so a fresh phone needs nothing else. 2026-11-07.
